# drain-kube-vip CAPD BGP test plan

This plan validates the `drain-kube-vip` control-plane teardown behavior in a
local CAPD cluster with kube-vip active/active BGP and host-mode FRR.

## Scope

- Validate normal kube-vip withdrawal from one control-plane node.
- Compare stale apiserver TCP behavior with and without `ss -K`.
- Reproduce the stale-ARP condition, where a downstream neighbor cache still
  maps the VIP to a drained control-plane node's MAC.
- Validate that explicitly removing the VIP from `lo` makes stale ARP recover.
- Collect enough logs and timing evidence to attach to the CWE MR.

## Baseline

Capture these before each scenario:

```bash
docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
docker exec bgp-containers vtysh -c 'show bgp summary'
docker exec bgp-containers vtysh -c 'show bgp ipv4 unicast'
docker exec <worker> bash -lc 'ip route; ip neigh show; ss -Htoni "( dst <vip> and dport = :6443 )"'
docker exec <target-cp> bash -lc 'hostname -I; ip -4 addr show lo; crictl ps --name kube-vip; ss -Htan state established "( sport = :6443 )"'
```

Record:

- Control-plane container IPs.
- Worker container IP.
- VIP address.
- FRR paths for the VIP /32.
- Existing worker client sockets to `VIP:6443`.
- Existing remote `VIP:6443` sockets on the target control-plane node.
- kube-vip container ID on the target node.

## Scenario 1: happy path, no forced socket kill

Goal: observe the natural behavior after kube-vip exits and BGP withdraws the
target node route, without using `ss -K`.

Steps:

1. Start worker-side `ss` watch for `dst <VIP> and dport = :6443`.
2. Start tcpdump from the FRR container/bridge for `host <VIP> and port 6443`,
   with a focused RST capture if traffic volume is high.
3. Move the kube-vip manifest out of `/etc/kubernetes/manifests` on the target CP.
4. Wait for the kube-vip container to exit.
5. Confirm FRR removed the target CP nexthop for the VIP /32.
6. Watch the worker-side sockets until they close, reset, or reconnect.
7. Capture kubelet and kube-proxy logs from the worker and target CP.

Pass criteria:

- kube-vip exits on the target CP.
- FRR withdraws the target CP path.
- No new remote `VIP:6443` sockets are established to the drained CP after route withdrawal.
- Worker-side `VIP:6443` sockets eventually close naturally or reconnect to a
  surviving control-plane path.
- kubelet/kube-proxy reconnect to a surviving control-plane node.

Measure:

- kube-vip manifest move timestamp.
- kube-vip exit timestamp.
- FRR withdrawal timestamp.
- first RST/FIN/retransmit observation.
- worker-side socket transition timestamp.
- kubelet/kube-proxy reconnect timestamp.

## Scenario 2: happy path, forced stale socket kill

Goal: compare the same drain with the runbook behavior that kills stale remote
`VIP:6443` sockets using `ss -K`, then waits for a quiet window.

Steps:

1. Restore kube-vip on a fresh/replacement CP, or use a fresh cluster/node.
2. Start worker-side `ss` watch for `dst <VIP> and dport = :6443`.
3. Start tcpdump on the target CP for `host <VIP> and port 6443` to capture the
   RST generated by `ss -K`.
4. Trigger node deletion through CWE so `drain-kube-vip` runs.
5. Confirm kube-vip exits and FRR withdraws the target CP path.
6. Confirm runbook logs show each stale remote socket closed with `ss -K`.
7. Confirm the 30s quiet window reports no new remote `VIP:6443` sockets.
8. Capture kubelet and kube-proxy logs from the worker and target CP.

Pass criteria:

- `drain-kube-vip` exits 0.
- kube-vip exits on the target CP.
- FRR withdraws the target CP path.
- runbook kills only remote sockets whose local endpoint is `VIP:6443`.
- no new remote `VIP:6443` sockets appear during the quiet window.
- kubelet/kube-proxy reconnect to a surviving control-plane node.

Measure:

- kube-vip manifest move timestamp.
- kube-vip exit timestamp.
- FRR withdrawal timestamp.
- `ss -K` timestamp per socket.
- quiet-window start/end timestamp.
- worker-side socket transition timestamp.
- kubelet/kube-proxy reconnect timestamp.

## Scenario 3: stale ARP reproduction

Goal: simulate a stale downstream ARP cache by forcing the worker to keep a
reachable neighbor entry that maps the VIP to the target CP MAC.

Steps:

1. Pick a target CP that currently has worker-originated `VIP:6443` sockets.
2. On the worker, map the VIP to the target CP MAC:

   ```bash
   docker exec <worker> bash -lc '
   VIP=<vip>
   CP_IP=<target-cp-ip>
   DEV=eth0
   MAC="$(ip -j neigh get "${CP_IP}" dev "${DEV}" | jq -r ".[0].lladdr")"
   ip neigh replace "${VIP}" lladdr "${MAC}" dev "${DEV}" nud reachable
   ip neigh show to "${VIP}" dev "${DEV}"
   '
   ```

3. Drain kube-vip on the target CP.
4. Confirm FRR withdraws the target CP path.
5. Confirm new remote `VIP:6443` sockets continue to appear on the drained CP.
6. Confirm `drain-kube-vip` fails because the 30s quiet window sees new remote tuples.

Expected failure:

- FRR route withdrawal succeeds.
- The worker still sends traffic directly to the target CP because of the stale
  reachable ARP entry.
- New remote `VIP:6443` sockets appear on the drained CP.
- `drain-kube-vip` fails instead of continuing teardown.

## Scenario 4: loopback VIP removal mitigation

Goal: validate the mitigation for kube-vip active/active BGP leaving the VIP on
`lo` after route withdrawal.

Steps:

1. Repeat the stale ARP setup from scenario 3.
2. Drain kube-vip on the target CP.
3. Remove the VIP from `lo` on the target CP:

   ```bash
   docker exec <target-cp> ip addr del <vip>/32 dev lo
   ```

4. Watch the worker neighbor entry and apiserver sockets:

   ```bash
   docker exec <worker> bash -lc 'watch -n1 "ip neigh show to <vip> dev eth0; ss -Htan state established | grep <vip> || true"'
   ```

5. Confirm kubelet/kube-proxy re-establish connections to surviving CP nodes.

Pass criteria:

- VIP is absent from target CP `lo`.
- The stale worker neighbor entry expires or becomes unusable within a few seconds.
- New `VIP:6443` sockets stop appearing on the drained CP.
- kubelet/kube-proxy recover through a surviving CP.

## Safety checks

Verify the runbook does not kill:

- local self-connections where peer IP is the VIP itself.
- `127.0.0.1` or `::1` apiserver sockets.
- node-IP apiserver sockets.
- unrelated `:6443` sockets on non-VIP local addresses.

## Evidence to attach

- FRR `show bgp summary` and `show bgp ipv4 unicast` before and after drain.
- `ip addr show lo` before and after drain.
- `ip neigh show` before and after stale ARP injection.
- worker-side `ss -Htoni "( dst <vip> and dport = :6443 )"` snapshots.
- target CP `ss -Htan state established "( sport = :6443 )"` snapshots.
- tcpdump snippets from FRR/worker/target CP, depending on the scenario.
- `/var/log/nke-execute-scripts.log` from the target CP.
- kubelet and kube-proxy logs from worker and target CP.
- final pass/fail summary with timing measurements.
