# nvke-controller

![Version: 0.0.0](https://img.shields.io/badge/Version-0.0.0-informational?style=flat-square) ![Type: application](https://img.shields.io/badge/Type-application-informational?style=flat-square) ![AppVersion: 0.0.0](https://img.shields.io/badge/AppVersion-0.0.0-informational?style=flat-square)

A Helm chart to deploy the NVKE controller service

## Additional tenant RBAC

`tenantAccess.additionalRBAC` defaults to `[]`. Set it to a list of Kubernetes
RBAC objects to append to the `nke-rbac` ConfigMap's `manifest.yaml`. Only
`Role`, `RoleBinding`, `ClusterRole`, and `ClusterRoleBinding` objects with
`apiVersion: rbac.authorization.k8s.io/v1` are accepted. `Role` and `RoleBinding`
require `metadata.namespace`; cluster-scoped kinds must omit it. The
tenant-access controller applies these objects to OIDC tenant clusters, not
the management cluster. Set `spiffe.trustDomain` and enable `tenantAccess`.
Helm rejects objects with the same kind, namespace, and name as built-in RBAC
or another additional entry.

User subjects are reserved for the shared management authenticator by default,
preventing operator-configured OIDC providers from impersonating service identities.
For users issued by an operator OIDC provider, annotate their `RoleBinding` or
`ClusterRoleBinding`:

```yaml
metadata:
  annotations:
    nvke.nvidia.com/identity-source: operator
```

This annotation applies to every User subject in the binding; keep management and
operator users in separate bindings. An absent annotation or `management` preserves
reservation. Operator JWT policy generation rejects other nonempty values.
Reserved username/group prefixes and the management SPIFFE trust domain remain
protected even with `operator`.
Use the final mapped username, including the OIDC provider's username prefix.
Group and ServiceAccount subjects do not add reserved usernames.

To remove an applied object, remove its entry and deploy the updated configuration,
then manually delete the object from each affected tenant cluster. Removing an
entry alone does not delete it; deleting it while still configured causes the
controller to recreate it.

## Renamed values

Two keys were renamed to the `nvke` prefix. The old names are no longer read,
and setting either one **fails the render** with an error naming its
replacement — Helm would otherwise drop an unknown key silently and leave the
setting at its default.

| Old key              | New key                          |
| -------------------- | -------------------------------- |
| `nkeOIDCAuth`        | [`nvkeOIDCAuth`](#values)        |
| `nkeSystemNamespace` | [`nvkeSystemNamespace`](#values) |

The sub-keys are unchanged, so migrating is a rename of the top-level key:
move `create` and `annotations` from `nkeSystemNamespace` to
`nvkeSystemNamespace`, and `enabled`, `tenantRbacName`, `issuerURL`,
`discoveryURL` and `caBundleSecret` from `nkeOIDCAuth` to `nvkeOIDCAuth`.

## Upgrading an existing site: names and identity

The chart's defaults are the names a **new** install gets. An install that
predates the `nvke` rename keeps the names it already runs, and it keeps them by
pinning. **Pin all of these before upgrading such a site**, together with the
management namespace in the next section:

```yaml
# The Deployment's spec.selector carries this value and is immutable, so an
# upgrade that changes it is REJECTED and the release fails.
nameOverride: cloud-workflow-engine

# Renaming a ConfigMap orphans the live object.
controllerConfig:
  name: nke-controller-config
apiAuth:
  configMap:
    name: nke-auth-config

# The SPIRE server of an existing site keeps issuing /nke-service/, and node
# agents older than the nvke rename admit only that path. Moving the segment
# makes every default RBAC subject match nothing, and breaks controller-to-node
# mTLS on a site that still manages such nodes. Keep the site's ClusterSPIFFEID
# and SPIRE admin ID on /nke-service/ to match.
spiffe:
  servicePathSegment: nke-service
```

`nameOverride` is the only one of these that fails loudly. The rest succeed and
leave something behind — an orphaned ConfigMap, RBAC subjects that match
nothing — so an upgrade that silently dropped a pin looks like a healthy
release.

**The `teleport.*` values are deliberately not in that list**, although their
own descriptions below say an existing site pins the old value. Those defaults
moved to `nvke-*` in a chart every existing site already runs, and no site ever
pinned them, so the old values are not what any site is running. Pinning them
now would be a behaviour change rather than a preservation. Treat those three
descriptions as describing a pin that is available, not one any site has taken.

`hack/testdata/chart-legacy-pinned-values.yaml` carries the same set as a
worked example, and `hack/chart-identity-assertions.py` renders the chart with
it and asserts every name comes out unchanged. That proves the chart still
honours the pins; it does not prove any particular site supplies them. **Check
the deployed values of every existing site before publishing a chart that
carries these defaults.**

## Upgrading an existing site: the management namespace

`nvkeSystemNamespace.name` defaults to `nvke-system`. A site installed before
that value existed holds its tenant-access Secrets — the per-cluster
`<cluster>-kubeconfig`, `<cluster>-admin-kubeconfig` and trust-bundle Secrets —
and its Cluster API objects in `nke-system`.

**Pin the old name before upgrading such a site:**

```yaml
nvkeSystemNamespace:
  name: nke-system
```

Unlike the label keys, the old namespace is not also read. Upgrading without the
pin does not fail: the chart creates `nvke-system`, moves the Roles and
RoleBindings into it, and the controller republishes there. What is left behind
is everything already in `nke-system`, including the kubeconfig Secrets Cluster
API and `nvkectl get kubeconfig` resolve by name.

`nvkectl get kubeconfig` reads `nvke-system` and then `nke-system`, so it keeps
working either way; `--namespace` names one outright.
